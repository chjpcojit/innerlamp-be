# Prospective vs Retroactive mode

Every spec generated by this skill is written in one of two modes. Ask the user which one applies
before generating anything (see `gathering_questions.md`) — the two modes fill the same four files
very differently.

## Prospective — spec written before the feature is built

Use when: the feature doesn't exist in code yet; the spec is meant to be handed to a Go developer
(or `go-clean-architecture`'s scaffolding guidance) as a work order.

- `requirements.md`: acceptance criteria describe the *intended* behavior. "Open questions" starts
  empty or with genuinely open design questions — there is no implementation to consult for
  answers.
- `design.md`: describes the *planned* architecture — which domain type, usecase, repository
  method, handler, route, and migration are expected. Any external call or table without a
  confirmed shape is explicitly called out as "planned, contract not yet confirmed", not written as
  if it already exists.
- `tasks.md`: every single item starts unchecked (`[ ]`). There is nothing to mark done yet.
- `changelog.md`: starts at `v1.0 (initial)`.

## Retroactive — spec written from an already-implemented feature

Use when: the feature already exists in the codebase (fully or partially) and the user wants the
spec to document it accurately — e.g. onboarding a new AI/human contributor, or catching up on
documentation debt.

- **Before writing `requirements.md`/`design.md`, read the actual code**:
  `services/appService/domain/<feature>.go` (entity + repository interface + sentinel errors),
  `services/appService/usecase/<feature>_usecase.go`,
  `services/appService/repository/postgres_<feature>_repository.go`,
  `services/appService/delivery/http/<feature>_handler.go`,
  the route wiring in `services/appService/cmd/main.go`,
  and the matching migration under `migrations/`.
- `requirements.md`: acceptance criteria describe what the shipped behavior *actually* does —
  don't describe an idealized version that doesn't match the code. If something is a stub or a
  route isn't protected, say so plainly in the "Pending" section, not folded into "done" criteria.
- `design.md`: the Layers & components table must name the actual files and symbols that exist, not
  hypothetical ones. Anything wired but not enforced (e.g. auth middleware that exists in `pkg/jwt`
  but is never wrapped around a route in `cmd/main.go`) gets its own "Deliberately stubbed for now"
  note explaining what's missing and why.
- `tasks.md`: mark `[x]` only for what you actually verified exists and works in the code; mark
  `[ ]` for anything missing, stubbed, or partially done. Don't trust a prior README or an older
  user-story doc's claims without spot-checking — retroactive specs exist specifically to correct
  documentation drift, not reproduce it.
- `changelog.md`: still starts at `v1.0 (initial)`, but its entry should say "written retroactively
  from the existing implementation".

## Mixed case: feature partially built

Common in practice — some phases done, others not. Treat it as Retroactive for the done parts and
Prospective for the rest, in the same four files (e.g. a feature whose domain + usecase + handler
exist and pass tests, but whose route is unauthenticated and whose repository method is only
exercised against a mock). Don't split into two separate spec sets.

## Migrated mode: a spec that predates this convention

Some modules in this repo already have a user-story file written before this skill existed (the
`docs/specs/features/<feature>/requirements.md` files migrated from the older
`docs/specs/features/<feature>/<feature>.md` layout, in Vietnamese, numbered US-0xx). When working
on one of those:

- Treat the existing content as `requirements.md` in a **prospective** state, but re-verify every
  claim against the code before marking anything `[x]` in `tasks.md` — those files were written
  before the implementation existed and have drifted (e.g. `content.md` describes client-side
  offline caching and Flutter packages, which are not this backend's concern at all).
- The migration only renamed the file; it did not convert prose acceptance criteria to EARS, remove
  client-only requirements, or split out `design.md`/`tasks.md`. Do not assume a migrated file is
  already spec-conformant.
